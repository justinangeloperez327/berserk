# Berserk v0.5.0

v0.5.0 focuses on application services. The goal is not a global facade layer; it is predictable, explicit service registration with request-scoped access.

## Application service registration

Applications can register optional services directly on the application instance:

```rust,ignore
app.cache(cache)?;
app.storage(storage)?;
app.events(events)?;
app.jobs(queue)?;
app.http_client(client)?;
app.notifications(notifier)?;
```

Each method is available only when its Cargo feature is enabled. Duplicate registration of the same service class is rejected during application setup.

## Request access

Handlers can retrieve the configured service without reaching into generic state manually:

```rust,ignore
fn show(request: Request) -> Result<Response> {
    let cache = request.cache()?;
    let storage = request.storage()?;
    let events = request.events()?;

    response().text("ready")
}
```

Cache, storage, outbound HTTP, event, and notification accessors return shared handles. Job queues remain cloneable handles owned by their worker infrastructure.

## Design boundary

The service APIs deliberately remain thin:

- no process-global service container;
- no runtime string aliases;
- no folder-based discovery;
- no hidden worker lifecycle;
- no automatic network clients or transports.

Applications still construct concrete implementations and own deployment-specific configuration.

## Reliability

v0.5.0 also carries the clippy correction required by the v0.4 authentication refactor and keeps the existing bounded cache, storage, event, job, notification, and outbound-client implementations.

## Compatibility

- Rust 1.88 remains the MSRV.
- Service features remain optional.
- Existing `App::state` and `Request::state/shared` APIs remain available for custom services.
