# Berserk v0.3.0 developer experience

Berserk v0.3.0 extends the existing framework rather than replacing its router, HTTP transport, or ORM. Rust 1.88 remains the MSRV. This release focuses on developer experience across responses, request input, controller ergonomics, middleware, application state/configuration, CLI scaffolding, and the foundation example.

## Responses

Import `response` and `redirect` from `berserk` or its prelude:

```rust,ignore
response().json(user)
response().json(users)
response().text("Hello")
response().status(201).header("X-Example", "value").json(user)
response().status(202).empty()
response().no_content()
redirect("/login")
response().status(303).redirect("/users")
```

Every factory terminal returns `Result<Response>`. Headers use the existing validated HTTP header implementation; an invalid header remains an error even if a later call supplies a valid value. Status and body compatibility are checked when the response is completed. Transport-owned framing headers remain forbidden.

`json` accepts `Json` or a type implementing `ApiResource`, including references, slices, vectors, and optional resources. Models must explicitly map public fields with `ApiResource`; no automatic model serialization or new serialization dependency is introduced. `Option::None` is JSON null, not a 404. Use `ok_or_else(Error::not_found)?` when absence should return 404.

`json(value)` emits the mapped value directly. `resource(value)` keeps the existing `{"data": ...}` envelope, and `collection(values)` keeps the collection envelope. `ResourceCollection::page` continues to provide pagination metadata. `created(value)` defaults to 201, `empty()` to 200, and `no_content()` to 204; an explicit factory status overrides these defaults. Existing `Response` constructors remain available.

Redirects default to 302 and accept only same-origin absolute paths, such as `/login` or `/users?page=2`. Schemes, protocol-relative URLs, backslashes, whitespace, and control characters are rejected. Redirect statuses are limited to 301, 302, 303, 307, and 308. Encode dynamic path segments, or use `app.path_for` for named routes.

## Request input

```rust,ignore
let email = request.input("email")?;          // Option<Json>
let page = request.query("page")?;            // Option<String>
let id = request.param("id");                 // Option<&str>
let token = request.header("Authorization"); // Option<&str>
let payload = request.json::<Payload>()?;
let input = request.validate::<CreateUserRequest>()?;
```

`input(name)` first reads a field from a JSON object body, then falls back to a query value represented as a JSON string. A present JSON null takes precedence over the query. Nonempty bodies must have the JSON content type and contain an object; empty bodies can use query input alone. Input lookup is not validation.

`query(name)` decodes `+` and percent escapes and rejects repeated values for the requested name. `query_pairs()` retains all decoded pairs when repeated keys are intentional. Invalid encoding returns a controlled 400 response. Existing `page_number()` still rejects duplicate, zero, malformed, or overflowing page numbers.

`json::<T>()` uses the existing `FromJson` trait. It decodes only: it does not sanitize, validate, or authorize. Use `json_value()` or `json::<Json>()` for raw JSON. Invalid JSON returns 400, a missing or unsupported content type returns 415, and typed field-decoding failures return 422.

`validate::<T>()` delegates to the established `FormRequest` lifecycle: decode, sanitize, validate, validate with request context, then authorize. `form_request::<T>()`, direct FormRequest action arguments, and `Validated<T>` remain available. Decode field types in `FromJson`; keep semantic rules in `validate` so sanitation happens first. Request-context database validation does not replace database constraints.

## Controllers and routes

Actions continue to request only what they need:

```rust,ignore
fn index() -> Result<Response> { /* ... */ }
fn show(id: u64) -> Result<Response> { /* ... */ }
fn store(request: Request) -> Result<Response> { /* ... */ }
fn update(id: u64, request: Request) -> Result<Response> { /* ... */ }

app.route().get("/users", index)?;
app.route().get("/users/{id}", show)?;
app.route().post("/users", store)?;
app.route().put("/users/{id}", update)?;
```

Primitive route values are parsed through the existing adapters in template order. Invalid conversion returns 400 without invoking the action. Registration rejects incompatible typed parameter counts. Manual `Request::param` access remains available.

`app.route().crud("/users", Users)?` remains the canonical model-bound resource shortcut for a `CrudController`. It registers these five API actions atomically, with route names such as `users.show`:

| Method | Path | Action |
| --- | --- | --- |
| GET | `/users` | index |
| POST | `/users` | store |
| GET | `/users/{id}` | show |
| PUT / PATCH | `/users/{id}` | update |
| DELETE | `/users/{id}` | destroy |

This shortcut uses the established typed model/FormRequest contract. Use individual verbs when actions instead take primitive IDs or a manual `Request`, as the historical v0.3 foundation example did. No new resource alias or HTML create/edit action is added. Existing compatibility APIs remain available.

## Middleware

Global, single-route, and group middleware all reuse the existing pipeline:

```rust,ignore
app.middleware(RequestId);
app.middleware(HandleErrors);
app.route().middleware(Audit).get("/users/{id}", show)?;
app.route().prefix("/api").middleware(AuthMiddleware).group(|routes| {
    routes.get("/users", index)?;
    routes.post("/users", store)
})?;
```

Layers enter in registration order and unwind in reverse order. `Next::run` consumes the continuation, preventing accidental double dispatch. A group is installed only if all its registrations succeed. Middleware types implement `Middleware::handle(Request, Next<'_>) -> Result<Response>`; compatible closures also work. The registrar is borrowed from an application, not a global router.

## Shared state and typed configuration

```rust,ignore
app.state(mail_service)?;
app.configure(AppConfig::from_env()?)?;

fn settings(request: Request) -> Result<Response> {
    let config = request.config::<AppConfig>()?;
    let mail = request.shared::<MailService>()?; // Arc<MailService>
    response().text(config.name.clone())
}
```

`App::configure` accepts a `Validate + Send + Sync + 'static` value and validates it at registration. `request.config::<T>()` borrows that configuration, returning an explicit error if absent. Configuration and services have distinct type-keyed entries, and duplicate registrations are rejected. The generated configuration module reads environment variables once at startup and reports invalid values explicitly.

`request.state::<T>()` still provides optional borrowed access to services. `request.shared::<T>()` returns an owned `Arc<T>` without cloning the service itself; it reports a missing registration as an error. The handle can outlive a request and can be passed explicitly to another task. Mutable services must supply their own Rust-safe synchronization.

Configuration access intentionally uses `Request`, rather than a process-global `config()` helper. Each application owns its state; there is no global mutable application registry. Register shared services and configuration on the root application, not inside `App::group`. Existing `app.database(...)`, lazy request connections, Claw scopes, and transaction APIs are unchanged.

## Optional transport and async

The `server` feature is enabled by default, preserving `App::bind` and `App::listen`. It selects the existing Tokio/Hyper HTTP transport. For in-memory routing without that runtime:

```toml
berserk = { path = "../berserk/crates/framework", default-features = false }
```

`App::handle` and `App::respond` remain available without `server`. Enable `server` explicitly when disabling defaults but still needing network serving. `async` independently opts into Tokio and the existing async action adapters; it does not implicitly enable the server. Synchronous database drivers still block their worker. No transport or middleware implementation is replaced.

## CLI and application skeleton

```sh
berserk new my-api
cd my-api
berserk make:controller UserController
berserk make:model User
berserk make:request CreateUserRequest
berserk make:middleware Audit
berserk serve
```

`serve` runs `cargo run` in the current application's directory, inherits its environment and terminal streams, and reports a failed child process. It is not a file watcher. Set `BERSERK_ADDRESS` (default `127.0.0.1:3000`) and `APP_NAME` (default `Berserk API`) to configure the generated application.

| Generated path | Purpose |
| --- | --- |
| `src/main.rs` | Explicit application assembly and serving |
| `src/controllers/` | Controller methods |
| `src/models/` | Claw models and public resource mappings |
| `src/requests/` | FormRequest input types |
| `src/middleware/` | Request/response middleware |
| `src/config.rs` | Typed environment configuration |
| `src/routes.rs` | Explicit route registration |

The root module declares all four generated folders, so new files registered in their `mod.rs` are reachable. Register generated controllers and middleware in routes yourself. Scaffolds enable `claw` for model generation, but do not select a database driver or install a database automatically. Models expose only their explicitly mapped fields. Existing safe-name/path checks and overwrite refusal remain in effect. Policy and resource generators remain available; policies require `auth`.

Generated manifests target Berserk 0.3. Repository development can use an equivalent local path dependency while retaining the required features.

## Foundation example and manual follow-up

At the v0.3 milestone, the foundation CRUD application demonstrated minimal action arguments, primitive IDs, manual Request validation, scoped Claw access, parameterized writes, pagination, JSON responses, status codes, and middleware. The current [foundation reference application](../examples/foundation/README.md) has since been expanded for the v1 maturity gate.

Release validation should cover response/header failures and redirects; typed JSON and repeated query input; sanitization, validation, and authorization order; state/configuration isolation and missing registrations; controller extraction and CRUD routing; middleware order; default/server/async feature combinations; and new-project/generator/serve behavior on Rust 1.88. The repository release workflows and release checklist remain the source of truth for release-gate evidence.
