# Phase 10 — JSON and validation

Added a standard-library-only JSON value/parser/encoder, explicit FromJson conversion trait, ValidateInput and reusable validation rules in crates/validation, request JSON/validated/query APIs, response JSON and input-error responses. Example: crates/framework/examples/json.rs. Run the json example with a Rust toolchain and POST application/json to /users. The endpoint demonstrates validation only, not persistence.

Numbers retain original valid numeric text; no float rounding or implicit coercion. Objects use sorted keys; duplicate keys rejected. Input and output nesting limited to 64. HTTP body limits bound input bytes at the server; direct Json::parse callers own byte-size limits. No JSON derive macros or streaming support. Parser is handwritten experimental code and requires fuzzing before production claims. Repeated query keys are retained; form decoding maps plus to space and requires UTF-8.

Request::json requires exactly one application/json Content-Type (parameters ignored). validated converts explicitly then runs validation. Required checks trim whitespace; length counts Unicode scalar values, not grapheme clusters. range applies to i64; applications supply bounds. Additional business rules use ValidationErrors::add. Error fields are an ordered array of field/code/message objects. Malformed JSON/query = 400, missing/unsupported content type = 415, validation = 422. In-memory App::handle propagates InputError; TCP server renders the JSON envelope. Server-rendered errors remain outside middleware response unwinding, so request-ID header coverage is not guaranteed for those errors.

Tests added for syntax failures, surrogate pairs, round-trip, nesting limits, content type, repeated query values, JSON response headers and validation accumulation. Source/manifests/archive reviewed. Compilation and all Rust tests remain unverified; earlier consumer gate remains pending. No third-party dependency or publication.
