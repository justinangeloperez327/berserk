# Berserk v0.2.0

Rust handles the machinery. Berserk tells the story of the web application.

The release keeps synchronous actions as the default and brings model binding, validated input, scoped database access, and responses together. The runnable [foundation example](../examples/foundation/README.md) contains a complete SQLite CRUD application. Rust 1.88 remains the MSRV. Packages are prepared at 0.2.0; publication is a separate owner action.

## Controllers and routing

Actions declare the data they need. A model parameter loads by the corresponding path parameter; a FormRequest parameter arrives after input validation and authorization.

```rust,ignore
fn index() -> Result<Response> {
    ResourceCollection::page(User::query().paginate(20)?).into_response()
}
fn show(user: User) -> Result<Response> {
    response().resource(user)
}
fn store(input: CreateUserRequest) -> Result<Response> {
    let user = User::create(input)?;
    Ok(response().resource(user)?.status(201))
}
fn update(mut user: User, input: UpdateUserRequest) -> Result<Response> {
    user.update(input)?;
    response().resource(user)
}
fn destroy(user: User) -> Result<Response> {
    user.delete()?;
    Ok(response().no_content())
}
```

Register these with `app.route().get/post/put/patch/delete`. `CrudController` provides the same five actions through methods on `&self`, associated `Model`, `Create`, and `Update` types, and atomic `route.crud("/users", Users)` registration. It creates `users.index`, `users.store`, `users.show`, `users.update` (PUT/PATCH), and `users.destroy`. Prefixes contribute to names. Existing `ApiResourceController`/`ResourceController` contracts remain available for applications that need explicit IDs and Request values.

`head` and `options` are available on Route and NamedRoute. GET still supplies a HEAD fallback. Static routes, named path encoding, atomic groups, route middleware, and root fallbacks retain their existing behavior.

## FormRequest

Implement `FromJson` to decode an explicit allowlist of fields, then `FormRequest`:

```rust,ignore
impl FormRequest for CreateUserRequest {
    fn sanitize(&mut self) { self.name = self.name.trim().into(); }
    fn validate(&self) -> ValidationResult {
        let mut errors = ValidationErrors::default();
        errors.length("name", &self.name, 1, 100);
        errors.email("email", &self.email);
        errors.finish()
    }
    fn authorize(&self) -> bool { Auth::check() }
}
```

Execution order is JSON decoding → sanitization → validation → `validate_request(&Request)` → `authorize_request(&Request)` → action. The default authorization hook uses `authorize()` (default true). Override the request-aware hook for policy checks requiring path parameters or application state. ValidateInput and `Validated<T>` remain supported as an alternative extraction contract.

Malformed JSON is 400, wrong content type is 415, field validation is 422, and a default authorization denial is 403. No action runs after extraction fails. Model parameters are resolved before body extraction; protect routes with authentication middleware when record existence is sensitive.

`validate_request` can query models for uniqueness or existence. Retain database UNIQUE/FOREIGN KEY constraints: a validation query cannot prevent concurrent writes. The foundation example demonstrates both a friendly uniqueness check and a UNIQUE constraint. Email validation accepts ordinary ASCII mailboxes; it does not implement every RFC address form or verify mailbox ownership.

## Claw models and writes

Models declare `TABLE`, decode rows, and supply `key()`. `PRIMARY_KEY` defaults to `id`; `parse_route_key` defaults to an unsigned integer and can be overridden for signed integers, strings, or UUID representations. The CLI uses a snake-case plural table name and an `i64` ID; applications can override both. No schema reflection, automatic timestamps, soft deletes, or implicit relationship queries are introduced.

`FILLABLE` explicitly lists columns allowed in typed `create` and `update`; the default empty list denies every column. Implement `IntoInsert<Model>` and `IntoUpdate<Model>` for input types to return column/value pairs. Primary keys, unknown columns, and repeated columns are rejected before executing SQL. Fixed arrays of `(&str, Value)` also implement these traits. There is deliberately no blanket JSON-to-model write conversion.

```rust,ignore
let user = User::find_or_fail(7)?; // missing model becomes 404 in HTTP
let users = User::where_("active", true)
    .where_op("score", ">=", 10)
    .order_by("id", Direction::Asc)
    .get()?;
let fresh = user.fresh()?;
```

`create` returns the inserted model. PostgreSQL/SQLite use RETURNING; MySQL retrieves by the driver's generated insert ID. For application-assigned keys, use the explicit connection API and reload explicitly. `update(&mut self, input)` reloads the model after writing. Use `Transaction::run` when multiple statements must be atomic. `PersistableModel::save()` writes the explicit `values_for_save()` mapping and rejects primary-key changes; this mapping is a separate trusted allowlist.

Connection-taking terminals use `_on` names: `find_on`, `get_on`, `save_on`, `create_on`, `update_on`, `delete_on`, `paginate_on`, and corresponding lifecycle helpers. Raw `_on` writes preserve the low-level execution result and accept trusted columns directly. Low-level `database::Query` retains its explicit connection and three-argument `where_` API. SQL values remain bound separately from SQL text.

## Database ownership and transactions

Register a `Database` once with `app.database(database)`. Each request receives a fresh scope. The first database operation acquires one owned connection; later operations reuse it. No connection is acquired by a request that does no database work. Applications choose pooling inside the acquisition function.

```rust,ignore
let user = Transaction::run(|| {
    let user = User::create(input)?;
    Audit::create(audit_input)?;
    Ok::<_, berserk::Error>(user)
})?;
```

The closure uses the active transaction for ordinary ORM calls. Success commits, an application error rolls back, and transaction failures propagate. Nested transactions are rejected. A panic unwinds through the driver's transaction guard; the request's connection lock becomes poisoned and subsequent access fails closed. Do not catch a transaction panic and continue database work in that same scope.

`request.connection()` remains an explicit, checked mutable borrow. Drop it before scoped ORM calls. Overlapping borrows return an error, rather than deadlocking or aliasing. `request.transaction(options, |connection| ...)` supports existing explicit-connection code. Use `_on` methods inside its closure because the passed connection is already borrowed.

Outside HTTP, use `DatabaseScope::new(database).run(|| ...)` or `with_scoped_connection(&mut connection, || ...)`. Scopes restore their predecessor on normal return and unwinding. The framework uses the established `scoped-tls-hkt` abstraction for borrowed lexical scopes; there is no local unsafe code or global default database. All scopes and transaction closures are synchronous: returning a future from `run` does not make the scope follow that future.

## Relationships and pagination

Existing typed `HasMany`, `HasOne`, and `BelongsTo` descriptors support `query.with(relation).get()`. Each relationship loads its keys in one bulk query and returns `RelatedSet`; access never triggers hidden SQL. Empty input executes no relationship query. HasOne rejects multiple related records for one parent. `with(a).with(b)` returns nested tuple relation results; eager pagination loads only the selected page's relationships. The API keeps relationships separate from models so ownership is explicit. Very large key batches may exceed driver parameter limits; page large collections.

`paginate(per_page)` reads one positive decimal `page` query parameter, defaults to 1, and rejects zero, duplicates, invalid integers, and offset overflow. Page sizes are 1–1000. Order explicitly for deterministic pages. Counts and item reads are separate statements; use a suitable transaction when a consistent snapshot matters. `ResourceCollection::page(page)` adds `current_page`, `per_page`, `total`, and `last_page` metadata; applications can add links with `.link(...)`.

## Responses, errors, and authorization

`Response`, `Json`, String, `&str`, unit (204), and framework `Result<T: IntoResponse>` are action outputs. `response()` provides json, text, created, no_content, resource, and collection helpers. ApiResource explicitly maps public fields; Resource wraps them in `data`, and ResourceCollection supplies arrays plus optional links/meta. Model values are not serialized automatically.

`Error::bad_request`, `unauthorized`, `forbidden`, `not_found`, `conflict`, and `rejected` produce JSON with `message` and `errors`. Input errors carry field/code/message entries. Missing database models map to 404, invalid input to 400, constraint conflicts to 409, and database timeouts to 503. Internal error details are redacted. Unauthorized responses include a Bearer challenge. Transport/protocol rejection remains distinct from application errors.

`App::handle` preserves errors for callers that need them. `App::respond` renders public errors. `HandleErrors` middleware renders inner errors so outer response decorators (request IDs, CORS, tracing) can still add headers. Middleware registration order is outer to inner; place HandleErrors after response decorators and before middleware whose errors should be rendered.

With `auth`, Authenticated uses the configured Guard, rejects duplicate Authorization headers, and attaches the Principal. `Auth::user/check/authorize/gate` access the current action's principal; Request::authorize is the explicit counterpart. `RequireAbility` uses a Gate in application state. Missing identity returns 401; a denied policy returns 403. Principals restore on return/unwind and are not inherited by spawned tasks. Applications still define browser cookie/CSRF policy, authorization rules, and persistent session storage.

## Optional async actions

Enable `async` and register actions with `get_async`, `post_async`, or another verb's `_async` variant. Named routes support these variants too. All synchronous extraction combinations are supported, including direct FormRequest input and scoped model pairs.

```rust,ignore
route.get_async("/users/{id}", |user: User| async move {
    let profile = external_service(user.id).await?;
    response().json(&profile)
})?;
```

Async actions run to completion on a blocking worker while Tokio drives their I/O. The action future is polled on that worker, so its request database and authorization scope survive awaits. Synchronous drivers still block that worker; this release does not pretend they are async database drivers. Avoid holding a connection borrow over an await. Spawned tasks do not inherit the request scope; pass owned values and install their own explicit scope for background database work.

From async callers use `Arc<App>::handle_async(request)`, especially on current-thread Tokio runtimes. Synchronous `handle` rejects async execution on a current-thread runtime. The HTTP transport already dispatches actions to blocking workers. Dropping handle_async, timing out a response, or disconnecting does not stop an action that has begun; writes may still complete. Transactions accept synchronous closures only. Keep worker concurrency and timeouts bounded through ServerConfig.

## Testing, generators, and release checks

TestClient uses App::respond so tests can assert the same public error responses. It offers request verbs, JSON bodies, status assertions, JSON paths, and validation-field assertions. App::handle remains available for direct error inspection. Existing fakes, event/job recorders, and temporary directories remain independent of production runtime code.

The CLI adds `make:controller`, `make:request`, `make:resource`, and `make:policy` alongside `make:model` and `make:migration`. Spaced `make <kind> <Name>` syntax is also supported. Generators validate names/paths and refuse overwrites. Files are registered in the generated folder's mod.rs; declare the folder module in your crate root. Model output needs `claw`, policy output needs `auth`. Adapt the explicit model fields, allowed columns, resource mapping, and policy before use; policies deny by default.

Run `python3 scripts/verify_generators.py` to compile generated output in a fresh external consumer. The [upgrade notes](upgrade-notes.md) list breaking changes. The [integration review](v0.2.0-review.md) records scope and validation evidence. Package publication, merging, tagging, and independent external review remain separate owner-controlled steps.
